# SDL3 输入后端（实验性）

本文说明 DeziroJoy 的 SDL3 输入后端：它是什么、如何在应用内显式启用、旧配置如何被
保守迁移、如何为普通 Joystick 补充标准映射、如何用独立探针验证设备、当前可用的诊断
手段，以及升级与回退方式。
（0.0.5-alpha.1 引入；alpha.2 起带保守旧配置迁移与输入刷新修复；alpha.3 起带普通
Joystick 映射补充流程；alpha.6 起应用内也可逐键学习，alpha.7 修复连续方向捕获。）

相关阶段定义见 [ROADMAP.md](../ROADMAP.md) 的 S1／S2；设备接入路线背景见
[NATIVE-GAMEPAD-ROADMAP.md](NATIVE-GAMEPAD-ROADMAP.md)。

## 状态与边界

- **SDL3 是默认输入后端（S3，0.0.5-alpha.5 起）**：新安装、从未选择过后端的升级、
  设置文件缺失或损坏，一律经 SDL3 统一 provider 读取；`input-backend.json` 中无法识别
  的取值按默认 SDL3 读取并说明原因。旧 XInput／evdev（现称「旧后端回退」）是**显式
  回退选项**，保留给仍生活在旧设备身份下的配置与可诊断回滚，尚未移除。
- SDL3 后端的目标是把 SDL3 能识别为标准 Gamepad 的设备接入现有
  “输入 → 分层／手势／DSL → 键鼠注入”管线，复用预设、临时层、前台规则、手势和 DSL，
  不先把设备转换成虚拟 Xbox 手柄，也不按品牌各写一套分支。
- **未经完整真机验收。** SDL3 provider、探针与设置卡片均有自动化测试（输入归一化、部署与
  生命周期语义，已包含在全量测试中）；USB／蓝牙、同型号双设备、不同 SDL Gamepad
  类型、休眠恢复等真机矩阵尚未验证。现有真机证据仅限**用户实测的 Xbox 布局手柄与
  Nintendo Switch 手柄全部按键可用（有限证据）**，不外推为全部设备已实测；SDL 能列出
  某种类型不等于该设备已实测，未实测设备明确标为未实测。
- **旧配置有保守迁移，但不是完整迁移。** 0.0.5-alpha.2 起，首次为 SDL3 设备运行时会把
  XInput／evdev 名下用户自己的预设按保守规则复制过来（见[旧配置迁移](#旧配置迁移保守桥接)）；
  只搬预设槽，不搬前台规则等全局状态，多设备歧义与布局反证时按设计跳过。真机与多设备
  证据待补。
- 本版**不包含**：触摸板／体感等 SDL3 扩展输入（S4）；旧后端移除与同物理设备去重验证
  （S3 剩余项）也未做。U1 通用控件面板与 U2 显示策略已于 0.0.5-alpha.3 实现（自动化
  测试；真实未知型号与真机场景待复验），见 [ROADMAP.md](../ROADMAP.md) U1／U2 节。
- 平台范围与产品一致：Windows 与 Linux；macOS 不是受支持平台。

## 启用与回退

1. 打开设置页「后台服务」卡片，找到其中的「输入后端」一节。选项为
   「SDL3 统一后端（默认）」与「旧后端回退（XInput / evdev）」；默认即 SDL3，无需操作。
2. 点击「**保存并重启常驻服务**」：选择写入配置目录根部的 `input-backend.json`
   （Windows `%APPDATA%\DeziroJoy\`、Linux `~/.config/DeziroJoy/`，取值 `sdl3`、
   `legacy`，以及早期 alpha 写入的 `platform`——后者仍被识别为旧后端），随后**安全重启
   常驻服务**——daemon 优雅停止（释放所有按住的键），新 daemon 启动时读取该文件。
   **没有运行中热切换**：provider 在 daemon 启动时创建，重启是应用切换的唯一诚实途径。
3. 卡片内的「运行中的后端：…」一行来自 daemon 快照，显示**真正在读取输入的后端**；
   保存后、重启前会提示「设置已改为 …，重启常驻服务后生效。」。重启失败时设置虽已保存，
   但 daemon 仍在原后端上运行并提示手动重启，不会静默更换。
4. **失败不静默回退**：选择了某个后端但启动失败（例如 SDL3 的原生运行时缺失）时，
   daemon 不会悄悄改读另一个后端，而是不带 provider 运行，启动摘要打印
   `input backend error: …`，卡片显示「后端启动失败：…（未切换回其他后端，当前不读取
   手柄输入）」。修复运行时或改选另一个后端即恢复。
5. 随时改选另一个后端并再次「保存并重启常驻服务」即完成切换；映射、预设、临时层、
   前台规则与输出通道都不因此改变（设备身份与配置匹配规则见下文各节）。

`input-backend.json` 缺失即默认 SDL3；文件损坏或取值无法识别时按默认 SDL3 读取，daemon
摘要给出回退原因，不报错崩溃。alpha.1–alpha.4 里显式选过旧后端的安装在升级后保持旧后端。

启用后，「连接」卡片与可视化器按 SDL3 报告的设备身份与布局显示；配置界面对 SDL3
设备使用**数据驱动的通用控件面板**（由设备输入描述按固定分区生成，不按型号绘图；面键
按设备字形决定逻辑按键，见[面键语义](#面键语义字形决定逻辑按键)），
没有输入描述的后端仍回退手绘模型；设备在 SDL3 中没有标准 Gamepad 映射时，不会伪装成
已有标准布局，需要先通过映射补充流程处理。首次
为 SDL3 设备运行时，若旧后端存在用户配置，会按[旧配置迁移](#旧配置迁移保守桥接)的
保守规则尝试一次复制，结果写在 daemon 启动摘要里。

## 面键语义：字形决定逻辑按键

SDL 的 south/east/west/north 是菱形里的四个**位置**，而每个位置上印的字因手柄而异。
逻辑按键按**设备报出的字形**决定，不按位置决定：

| 设备 | south（南） | east（东） | west（西） | north（北） |
|---|---|---|---|---|
| Xbox／DualShock | A | B | X | Y |
| 任天堂（SDL 报 BAYX） | B | A | Y | X |
| GameCube（SDL 报 AXBY） | A | X | B | Y |
| SDL 读不到字形 | A | B | X | Y（位置回退） |

- `Sdl3FaceButtonMap` 读 SDL 报给每台设备的字形（`SDL_GetGamepadButtonLabel`，记录在
  `Sdl3GamepadInfo.FaceButtonLabels`，按 south/east/west/north 序），据此得出每个位置的
  逻辑按键；读不到字形时回退位置表（Xbox 约定，也是所有 SDL 可识别布局共享的解释）。
- **标签与执行同一来源**：状态 tracker 与控件描述都用这一张表——面板上叫 X 的控件绑定的
  就是“按下物理 X 产生的那次输入”。此前按位置固定映射会让任天堂手柄的物理 X（北位）
  执行逻辑 Y（面板显示 X、映射执行 Y）；只改显示不改语义是治标。
- 设备重映射时 tracker 随新字形表整体更换：旧布局下按住的键不会以新名字残留。
- **DInput 映射设备保持位置语义**：经 `map` 流程补充映射的设备报不出 SDL 可识别的字形，
  每个槽取位置表答案——这正是手写映射时的假定（取证流程的键就是 SDL 的位置键）。
- 映射卡片里原始扩展码的显示与通用面板使用同一套名称，两处不会各说各话。

## 设备身份

SDL3 provider 的持久身份由 SDL 跨运行稳定的字段组合而成，实例 ID 只用于本次运行：

- DeviceId 形如 `sdl:{guid}[:{serial}][:{path}]`：GUID 必有；有序列号时用序列号区分同型号
  多设备；无序列号但有路径时用路径（换端口可能改变）；两者皆无时追加本次运行的实例 ID，
  并在扫描诊断中标注该身份不稳定——重启后配置可能无法自动重新关联。
- SDL 的 gamepad 类型记录在身份与探针输出中，但**不**进 DeviceId：SDL 映射库更新把设备
  重分类（如 Standard → Xbox360）时，不应让用户已保存的配置失效。
- 该身份与 XInput／evdev 的身份互不通用；旧配置到 `sdl:` 身份的自动迁移**尚未实现**
  （S2 待完成项）。

## 旧配置迁移（保守桥接）

两个后端按不同身份保存配置（XInput 用 `xinput:N`、evdev 用 `/dev/input/eventN`、
SDL3 用 `sdl:{guid}[:{serial}][:{path}]`），直接切换后端会让旧配置孤立在磁盘上、
新设备跑库默认值。0.0.5-alpha.2 起的迁移是两者之间的保守桥接，规则按优先级如下：

1. **只迁到 SDL 设备**：非 SDL 设备的键里本来就持有自己的配置，绝不触碰。
2. **一对一才动**：旧配置设备与当前连接的 SDL 设备必须都恰为一个。多设备（无论哪边
   多于一个）整体跳过并说明计数——运行时玩家索引是分配而非身份，不作为证据。
3. **布局反证跳过**：新旧设备都报告了具体但不同的布局时，判定不是同一只手柄，拒绝
   迁移；该决定同样记入 marker，重启不重复询问。
4. **逐槽原样复制**：槽号不变（Leader 键命名它切换的两个槽，手势、层与特殊键随配置
   体过去），只复制用户自己的槽；**旧文件只读**，新键写在旁边。
5. **只覆盖空白**：仅当 SDL 设备同号槽缺失、或可逐字段证明是未改动的库默认值时才
   复制；用户已在 SDL 下自定义的槽一律保留并说明——早期 alpha 已开始配置的用户不会
   被回填。
6. **持久 marker 防重复**：配置目录根部 `legacy-migration.json`（与
   `input-backend.json` 同处 profiles 目录之外）记录已处理配对；重连、重启、第二个
   窗口都不会二次复制——用户删掉的槽不会被重新填回，重置为默认的槽不会被旧配置悄悄
   替换。marker 损坏时按“无法证明任何配对是新的”处理，**宁可不迁移也不覆盖**。

迁移在新设备首次进入引擎主机时执行（早于默认配置落地），daemon 启动摘要逐条打印
复制与跳过原因（`legacy config migration: …`）。它只覆盖预设槽；前台规则等全局状态
不在迁移范围内。

## 映射补充：为普通 Joystick 生成标准映射

只能作普通 Joystick 枚举、没有可靠 SDL Gamepad 映射的设备（典型为 DInput 时代的手柄）
此前不在支持声明内。映射补充流程让它有机会进入同一通用读取路径；它不维护型号白名单、
不猜未知布局，做的是**逐键取证**。

### 应用内逐键学习（0.0.5-alpha.6 起；alpha.7 起可重学）

1. 打开「设置 → 后台服务」，选择 SDL3 后端，在「手柄布局学习（SDL）」中重新扫描。
   下拉框列出 SDL 实际看到的 HID 接口及按钮／轴／方向帽数量；未映射、已有自定义映射和
   SDL 已有标准映射的设备都可选择，已有映射标注“可重学”。同一物理手柄可能有多个接口，
   默认选中按钮和轴较多的一个，也可手动更改。
2. 点击「逐键学习并保存」，在窗口中按提示操作真实控件。按钮、轴和方向帽都可捕获；没有
   某项时点「跳过此项」，点「取消」则不写入任何映射。向导复用下方 CLI 的同一个捕获会话、
   SDL 校验与原子保存实现，不按 VID／PID 猜测布局。
3. SDL 接受后映射写入同一个 `sdl-mappings.json`；应用随后调用既有「保存并重启常驻服务」
   路径。重连后的 daemon 快照才是设备已经进入统一输入管线的证据。已有同 GUID 映射会更新，
   其他设备条目保持不变；文件不可完整读取时拒绝覆盖。布局学习只定义物理控件与标准逻辑
   按键的对应，动作预设仍在 profiles 中独立定义这些逻辑按键执行什么。

Windows 上同一物理复合 HID 的多个 `COLxx` 接口若被 SDL 认成多个 Gamepad，provider 只让
原始按钮／轴／方向帽更丰富的接口进入 daemon，避免两个接口各执行一套动作预设。分组依据是
HID 路径中的物理实例，不是 VID／PID；不同物理实例不会被合并，已有配置文件也不会被删除。

以下 CLI 步骤仍保留，供诊断、无 GUI 环境和脚本使用：

1. **看谁缺映射**：探针 `joysticks` 列出缺少标准 Gamepad 映射的普通 Joystick——GUID、
   名称、路径、VID／PID、原始按键／轴／方向帽计数（写映射的依据）；已有标准映射的
   设备单独计数。同时打印当前映射文件内容。
2. **逐键取证**：探针 `map`（可 `--guid=` 直接指定设备）依次提示 21 个必需项（面键
   四枚、十字键四向、start／back／guide、左右肩键、左右摇杆点击、左右摇杆 X／Y、
   左右扳机）与 6 个可选项（截屏／分享、背键 1–4、触摸板）；`s` 跳过（设备没有该项）、
   `q` 取消整个流程。刚捕获的同一控件须先回中；上一帧未选中的残留活动控件不会串到下一步。
   约 60 Hz 采样且每次采样前泵一次 SDL；轴先拓宽为 `int` 再取绝对值，`-32768` 合法。
   扳机与轴式十字键按半轴 `+aN`／`-aN`、摇杆轴按 `aN`、仅在轴向
   反向时加 `~`。
3. **先校验再交给 SDL**：生成的映射先过本地校验（32 位 GUID、名称、控件值形态），
   再 `SDL_AddGamepadMapping`；被 SDL 拒绝的映射**不会**写入文件。保存前明确列出
   跳过了哪些项（跳过的必需项结尾再次点名）——映射是不完整但诚实的描述，不把设备
   伪装成已有完整标准布局。
4. **落盘**：保存到配置根目录的 `sdl-mappings.json`（与 `input-backend.json` 同处
   profiles 目录之外），条目为 guid／name／mapping／updatedUtc；mapping 即
   `SDL_AddGamepadMapping` 接受的文本，可手编。同一 GUID 重复映射是**更新**而非追加；
   写入原子（临时文件 + 替换），daemon 与探针读到旧整体或新整体。文件损坏或不可读时
   **宁可不映射也不覆盖**：本次运行只使用 SDL 内置映射库，扫描诊断给出
   `持久 SDL 映射文件（sdl-mappings.json）读取失败：…`。
5. **重启后进入映射路径**：provider 在 SDL 初始化成功后、第一次枚举之前逐条
   `SDL_AddGamepadMapping`——SDL 在构建手柄列表时就决定一个 Joystick 是不是标准
   Gamepad。SDL 3.4.20 起 `SDL_AddGamepadMapping` **立即重新评估**已连接（含此前
   已枚举）的设备，因此探针保存映射后可以当场确认设备已被认作标准 Gamepad；但
   **daemon 只在启动时读一次** `sdl-mappings.json`（它早于第一次枚举加载），映射要
   进入实际映射路径仍需**重启常驻服务**。文件损坏或不可读时**宁可不映射也不覆盖**：
   本次运行只使用 SDL 内置映射库，扫描诊断给出
   `持久 SDL 映射文件（sdl-mappings.json）读取失败：…`。

`map` 在标准输入被重定向（CI、管道）时不阻塞：打印待映射设备的 GUID 与名称后以退出码
2 退出；没有待映射设备时直接说明并以 0 退出。详细命令与选项见
`tools/Sdl3Probe/README.md`。

边界：映射补充只覆盖用户实际映射过的设备，**不代表全部 DInput 设备已支持**；它与 U1
通用控件面板（alpha.3 已实现）是两件事，不互相代表完成。Windows 真机 `3537:1041` 已完成
按钮、方向帽和双摇杆学习，保存映射与 daemon 主接口接管已核对；通用高亮、新增动作及多物理
设备场景继续按人工验收清单第 30 节复验。

## 部署：SDL3 运行时随包分发

SDL3 通过 SDL3-CS 绑定与每平台原生运行时接入：发布产物中包含托管绑定程序集与当前 RID 的
原生库（Windows 为 `SDL3.dll`，Linux 为 `libSDL3.so`）。四种发布包（Windows setup、deb、
rpm、AppImage）都原样载荷 publish 输出，打包脚本与发布工作流用同一套断言
（`tools/Packaging/verify-sdl3-assets.sh` 及 Windows 侧对应检查）确认这些资产确实在包内——
缺失会在这里失败，而不是在用户机器上表现为“没有输入后端”。

## 探针：接入产品前先验证设备

仓库内置独立 SDL3 探针 `tools/Sdl3Probe`（与 `tools/GameInputProbe` 同级的独立 dotnet 工具，
不属于产品构建，也未接入产品 provider）。它面向 S1 的部署与枚举验证，用来在启用 SDL3
之前回答“这只手柄在 SDL3 里是什么”：

```sh
# 一次性扫描：SDL3 运行时 + 每台识别出的手柄，以及与旧后端枚举的对照
dotnet run --project tools/Sdl3Probe -- list
dotnet run --project tools/Sdl3Probe -- list --json   # 机器可读

# 持续监听：热插拔转换 + 引擎将消费的归一化状态（按钮、双摇杆、扳机）
dotnet run --project tools/Sdl3Probe -- watch
dotnet run --project tools/Sdl3Probe -- watch --interval=100 --duration=60

# 映射补充：列出缺少标准 Gamepad 映射的普通 Joystick；为其中一台逐键生成映射
dotnet run --project tools/Sdl3Probe -- joysticks
dotnet run --project tools/Sdl3Probe -- map
dotnet run --project tools/Sdl3Probe -- map --guid=03000000790000000006000000000000
```

- `list` 走 provider 自己的探测路径，输出与 daemon 扫描诊断**同一来源**：SDL3 运行时版本、
  每台设备的类型、GUID、VID／PID、序列号、路径、运行内实例 ID、player index、连接状态、
  SDL 映射来源与映射、面键标签、声明按钮数，以及触摸板／传感器等扩展能力计数（只记录，
  不计入标准输入支持）；
- 同时打印旧后端（XInput／evdev）当前枚举到的设备，用于识别“同一物理设备被两边看到”
  的重复设备，为迁移期去重与身份映射建立证据；
- `watch` 保持 provider 打开，打印连接／断开转换与归一化状态；打开失败的设备带 SDL 自己
  的错误文本，身份回退为实例 ID 的设备单独列出；每 2 秒打印一次实际状态泵入速率——
  健康时与监听间隔一致，若吸附在扫描间隔（约 4/s）即输入不跟手缺陷复现；
- `joysticks`／`map` 是[映射补充](#映射补充为普通-joystick-生成标准映射)流程的入口：
  前者只列缺少标准映射的普通 Joystick 并打印当前映射文件，后者逐键取证并写入
  `sdl-mappings.json`（保存后重启常驻服务生效）；
- 退出码：0 成功、1 SDL3 运行时不可用（或映射被 SDL 拒绝、写入失败）、2 用法错误，
  或 `map` 需要交互式终端而标准输入已被重定向。

构建、发布（含原生库）与该探针的本机运行结果见 `tools/Sdl3Probe/README.md`。探针不注入
键鼠、不改变产品默认后端；除 `map` 按用户明确操作写入 `sdl-mappings.json` 外不修改任何
配置。它的输出是判断“某设备是否进入 SDL3 统一读取路径”的证据，不代表该设备已完成支持
验收。

## 诊断

- **daemon 启动摘要**（Linux `journalctl --user -u dezirojoy-daemon`；Windows 计划任务
  运行需重定向 stdout）在既有行之外新增：
  - `input backend: 平台默认（Windows · XInput）`／`平台默认（Linux · evdev）`／
    `SDL3 统一后端（实验性，需手动启用）`——当前真正在用的后端；
  - `input backend error: …`——显式选择的 SDL3 启动失败及原因；
  - `input backend settings: …`——设置文件损坏时的回退原因；
  - `legacy config migration: …`——旧配置迁移复制了哪些槽，或为何跳过（多设备歧义、
    布局反证、目标槽已自定义、marker 不可读等，逐条说明）。
- **SDL3 扫描诊断**（daemon 摘要与 GUI 状态区同一来源，四种结局各带中文指引）：
  - `SDL3 运行时不可用，无法检测手柄`——确认应用分发了当前平台的原生 SDL3 运行时；
  - `SDL3 已初始化，但没有识别为标准 Gamepad 的手柄`——只能作普通 Joystick 枚举的设备
    需要先补充映射，不能当作已有标准布局；指引现在直接点名探针 `map` 流程与
    `sdl-mappings.json`（见[映射补充](#映射补充为普通-joystick-生成标准映射)）；
  - `SDL3 报告了 N 个手柄，但有 M 个无法打开`——附打不开的设备与 SDL 错误文本；
  - `持久 SDL 映射文件（sdl-mappings.json）读取失败：…`——本次运行只使用 SDL 内置
    映射库，`map` 流程生成的映射没有生效；扫描同时报告载入了几条持久映射
    （`AppliedMappingCount`），"没有映射文件"与"有但没生效"因此可区分；
  - 另有“无序列号也无路径、身份回退实例 ID”的单独提示（见[设备身份](#设备身份)）。
- **设置页「后台服务」卡片的「输入后端」一节**显示三行状态：「运行中的后端：…」
  （daemon 快照报告的实际后端）、「后端启动失败：…（未切换回其他后端，当前不读取手柄
  输入）」（显式选择启动失败时）、「设置已改为 …，重启常驻服务后生效。」（已保存但
  daemon 尚未重启到新后端时）。界面显示的是真正在读取输入的后端，而不是用户上次选择
  的那一个。
- **设置页「注入状态」卡片**不变：实际注入者身份、已注入／已阻止计数与最近错误。

## 升级与回退

- **升级到 0.0.5-alpha.5 默认后端变为 SDL3**：配置位置不变（Windows
  `%APPDATA%\DeziroJoy\`、Linux `~/.config/DeziroJoy/`），旧后端配置不被改写；从未
  选择过后端的安装（含从 0.0.2 或更早直接升级）升级后按 SDL3 读取，alpha.1–alpha.4
  里显式选过旧后端的安装保持旧后端。
- **自动更新会提供本 alpha**：应用内更新按语义版本选取最新发布（包含预发布），
  0.0.2 正式版用户检查更新会看到 0.0.5-alpha.7。不想升级 alpha 的用户请在设置页关闭
  “启动时检查更新”与自动下载，或到发布页手动选择版本安装。
  `0.0.2-beta.3` 及更早版本的应用内自动更新存在缺陷，从那些版本升级请手动下载
  （README「安装」一节有同样说明）。
- **回退**：设置页「后台服务」卡片选「旧后端回退（XInput / evdev）」并保存重启；或重新
  安装 0.0.2——两种方式都保留配置。旧后端在本版保留（显式回退选项），回退可控。
- **设备身份与迁移边界（重要）**：SDL3 的设备身份是独立的 `sdl:` 前缀 ID。alpha.2
  起的保守迁移会在**一对一且无反证**时把旧后端预设逐槽复制过来；多设备歧义、布局
  明显不同、或 SDL 槽已被自定义时按设计跳过——此时同一只手柄会作为新设备使用默认
  配置，而旧配置仍原样留在磁盘上（切回旧后端后照旧可用）。这是已知边界，
  不是配置丢失；真实旧配置组合与多设备场景的证据待补。

## 已知限制

- SDL3 provider 与探针均未经完整真机验收；覆盖声明按 SDL 版本和能力记录，不以少数
  型号的成功推导为所有设备已实测。现有真机证据仅限用户实测的 Xbox／NS 全部按键
  可用（有限证据）。
- **S3 默认切换已落地但验收未完成**：同物理设备被 SDL3 与旧后端同时看到的去重验证、
  旧后端移除未做；真实设备矩阵、同型号双设备、Joy-Con 形态、休眠恢复与回退路径的
  真机验收待补。
- 面键语义按字形：SDL 读不到字形的设备回退位置表；GameCube 等布局的正确性依赖 SDL
  报表的字形，需真机复核。DInput 映射设备保持位置语义（设计如此）。
- 映射补充只覆盖用户实际映射过的设备；DInput／普通 Joystick 映射流程与 Windows
  更新（证实停止门、用户语境链）的真机复验待补；映射保存后 SDL 立即认账（探针可当场
  确认），daemon 需重启常驻服务才进入映射路径。
- 旧配置迁移是保守初始实现：只搬预设槽、只在一对一且无反证时搬、marker 防二次复制；
  多设备歧义、Joy-Con 形态与真实旧配置组合的真机证据待补，前台规则等全局状态不在
  迁移范围。
- 后端切换需要重启（daemon 启动时读取设置），没有运行中热切换。
- 触摸板、体感等扩展输入不在本版范围（S4）；设备未申报或未验证的能力保持禁用。
- Windows 上旧后端（XInput）无法读取 Guide 键这一限制随回退选项保留；SDL3 后端在各
  平台报告 Guide，其实际可用性取决于设备与映射。
