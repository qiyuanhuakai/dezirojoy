# SDL3 输入后端（实验性）

本文说明 0.0.5-alpha.1 引入的 SDL3 输入后端：它是什么、如何在应用内显式启用、如何用独立
探针在接入前验证设备、当前可用的诊断手段，以及升级与回退方式。

相关阶段定义见 [ROADMAP.md](../ROADMAP.md) 的 S1／S2；设备接入路线背景见
[NATIVE-GAMEPAD-ROADMAP.md](NATIVE-GAMEPAD-ROADMAP.md)。

## 状态与边界

- **默认后端没有改变。** Windows 仍默认 XInput + SendInput，Linux 仍默认 evdev + uinput；
  本版不做 S3 的默认切换，SDL3 只是设置中的一个**显式实验选项**。
- SDL3 后端的目标是把 SDL3 能识别为标准 Gamepad 的设备接入现有
  “输入 → 分层／手势／DSL → 键鼠注入”管线，复用预设、临时层、前台规则、手势和 DSL，
  不先把设备转换成虚拟 Xbox 手柄，也不按品牌各写一套分支。
- **未经真机验收。** SDL3 provider、探针与设置卡片均有自动化测试（输入归一化、部署与
  生命周期语义，已包含在本版全量测试中）；USB／蓝牙、同型号双设备、不同 SDL Gamepad
  类型、休眠恢复等真机矩阵尚未验证。SDL 能列出某种类型不等于该设备已实测，未实测设备
  明确标为未实测。
- **旧配置不会被自动迁移。** XInput／evdev 的按设备配置保持原样；SDL3 使用自己的设备
  身份（`sdl:` 前缀，见[设备身份](#设备身份)），同一只手柄切到 SDL3 后可能被当作新设备，
  见[升级与回退](#升级与回退)。
- 本版**不包含**：U1 通用控件面板、U2 输入显示策略、S3 默认切换，也不包含触摸板／体感等
  SDL3 扩展输入（S4）。
- 平台范围与产品一致：Windows 与 Linux；macOS 不是受支持平台。

## 启用与回退

1. 打开设置页「后台服务」卡片，找到其中的「输入后端」一节。默认选项为
   「平台默认（XInput / evdev）」，选择「SDL3 统一后端（实验性）」即启用。
2. 点击「**保存并重启常驻服务**」：选择写入配置目录根部的 `input-backend.json`
   （Windows `%APPDATA%\DeziroJoy\`、Linux `~/.config/DeziroJoy/`，取值 `platform`
   或 `sdl3`），随后**安全重启常驻服务**——daemon 优雅停止（释放所有按住的键），
   新 daemon 启动时读取该文件。**没有运行中热切换**：provider 在 daemon 启动时创建，
   重启是应用切换的唯一诚实途径。
3. 卡片内的「运行中的后端：…」一行来自 daemon 快照，显示**真正在读取输入的后端**；
   保存后、重启前会提示「设置已改为 …，重启常驻服务后生效。」。重启失败时设置虽已保存，
   但 daemon 仍在原后端上运行并提示手动重启，不会静默更换。
4. **失败不静默回退**：显式选择了 SDL3 但启动失败（例如原生运行时缺失）时，daemon 不会
   悄悄改读平台后端，而是不带 provider 运行，启动摘要打印
   `input backend error: …`，卡片显示「后端启动失败：…（未切换回其他后端，当前不读取
   手柄输入）」。修复运行时或切回平台默认即恢复。
5. 随时切回「平台默认（XInput / evdev）」并再次「保存并重启常驻服务」即完成回退；
   映射、预设、临时层、前台规则与输出通道都不因此改变。

`input-backend.json` 缺失即平台默认；文件损坏或取值无法识别时按平台默认读取，daemon
摘要给出回退原因，不报错崩溃。

启用 SDL3 后，「连接」卡片与可视化器按 SDL3 报告的设备身份与布局显示；设备在 SDL3 中
没有标准 Gamepad 映射时，不会伪装成已有标准布局，需要先通过映射补充流程处理。

## 设备身份

SDL3 provider 的持久身份由 SDL 跨运行稳定的字段组合而成，实例 ID 只用于本次运行：

- DeviceId 形如 `sdl:{guid}[:{serial}][:{path}]`：GUID 必有；有序列号时用序列号区分同型号
  多设备；无序列号但有路径时用路径（换端口可能改变）；两者皆无时追加本次运行的实例 ID，
  并在扫描诊断中标注该身份不稳定——重启后配置可能无法自动重新关联。
- SDL 的 gamepad 类型记录在身份与探针输出中，但**不**进 DeviceId：SDL 映射库更新把设备
  重分类（如 Standard → Xbox360）时，不应让用户已保存的配置失效。
- 该身份与 XInput／evdev 的身份互不通用；旧配置到 `sdl:` 身份的自动迁移**尚未实现**
  （S2 待完成项）。

## 部署：SDL3 运行时随包分发

SDL3 通过 SDL3-CS 绑定与每平台原生运行时接入：发布产物中包含托管绑定程序集与当前 RID 的
原生库（Windows 为 `SDL3.dll`，Linux 为 `libSDL3.so`）。四种发布包（Windows setup、deb、
rpm、AppImage）都原样载荷 publish 输出，打包脚本与发布工作流用同一套断言
（`tools/Packaging/verify-sdl3-assets.sh` 及 Windows 侧对应检查）确认这些资产确实在包内——
缺失会在这里失败，而不是在用户机器上表现为“没有输入后端”。

## 探针：接入产品前先验证设备

仓库内置独立 SDL3 探针 `tools/Sdl3Probe`（与 `tools/GameInputProbe` 同级的独立 dotnet 工具，
不属于产品构建，也未接入产品 provider）。它面向 S1 的部署与枚举验证，用来在启用 SDL3
之前回答“这只手柄在 SDL3 里是什么”：

```sh
# 一次性扫描：SDL3 运行时 + 每台识别出的手柄，以及与旧后端枚举的对照
dotnet run --project tools/Sdl3Probe -- list
dotnet run --project tools/Sdl3Probe -- list --json   # 机器可读

# 持续监听：热插拔转换 + 引擎将消费的归一化状态（按钮、双摇杆、扳机）
dotnet run --project tools/Sdl3Probe -- watch
dotnet run --project tools/Sdl3Probe -- watch --interval=100 --duration=60
```

- `list` 走 provider 自己的探测路径，输出与 daemon 扫描诊断**同一来源**：SDL3 运行时版本、
  每台设备的类型、GUID、VID／PID、序列号、路径、运行内实例 ID、player index、连接状态、
  SDL 映射来源与映射、面键标签、声明按钮数，以及触摸板／传感器等扩展能力计数（只记录，
  不计入标准输入支持）；
- 同时打印旧后端（XInput／evdev）当前枚举到的设备，用于识别“同一物理设备被两边看到”
  的重复设备，为迁移期去重与身份映射建立证据；
- `watch` 保持 provider 打开，打印连接／断开转换与归一化状态；打开失败的设备带 SDL 自己
  的错误文本，身份回退为实例 ID 的设备单独列出；
- 退出码：0 成功、1 SDL3 运行时不可用、2 用法错误。

构建、发布（含原生库）与该探针的本机运行结果见 `tools/Sdl3Probe/README.md`。探针不注入
键鼠、不修改配置、不改变产品默认后端；它的输出是判断“某设备是否进入 SDL3 统一读取路径”
的证据，不代表该设备已完成支持验收。

## 诊断

- **daemon 启动摘要**（Linux `journalctl --user -u dezirojoy-daemon`；Windows 计划任务
  运行需重定向 stdout）在既有行之外新增：
  - `input backend: 平台默认（Windows · XInput）`／`平台默认（Linux · evdev）`／
    `SDL3 统一后端（实验性，需手动启用）`——当前真正在用的后端；
  - `input backend error: …`——显式选择的 SDL3 启动失败及原因；
  - `input backend settings: …`——设置文件损坏时的回退原因。
- **SDL3 扫描诊断**（daemon 摘要与 GUI 状态区同一来源，四种结局各带中文指引）：
  - `SDL3 运行时不可用，无法检测手柄`——确认应用分发了当前平台的原生 SDL3 运行时；
  - `SDL3 已初始化，但没有识别为标准 Gamepad 的手柄`——只能作普通 Joystick 枚举的设备
    需要先补充映射，不能当作已有标准布局；
  - `SDL3 报告了 N 个手柄，但有 M 个无法打开`——附打不开的设备与 SDL 错误文本；
  - 另有“无序列号也无路径、身份回退实例 ID”的单独提示（见[设备身份](#设备身份)）。
- **设置页「后台服务」卡片的「输入后端」一节**显示三行状态：「运行中的后端：…」
  （daemon 快照报告的实际后端）、「后端启动失败：…（未切换回其他后端，当前不读取手柄
  输入）」（显式选择启动失败时）、「设置已改为 …，重启常驻服务后生效。」（已保存但
  daemon 尚未重启到新后端时）。界面显示的是真正在读取输入的后端，而不是用户上次选择
  的那一个。
- **设置页「注入状态」卡片**不变：实际注入者身份、已注入／已阻止计数与最近错误。

## 升级与回退

- **升级到 0.0.5-alpha.1 不改变现有行为**：配置位置不变
  （Windows `%APPDATA%\DeziroJoy\`、Linux `~/.config/DeziroJoy/`），默认后端不变，
  旧配置不被改写；不显式启用 SDL3 时，升级后与 0.0.2 的使用方式一致。
- **自动更新会提供本 alpha**：应用内更新按语义版本选取最新发布（包含预发布），
  0.0.2 正式版用户检查更新会看到 0.0.5-alpha.1。不想升级 alpha 的用户请在设置页关闭
  “启动时检查更新”与自动下载，或到发布页手动选择版本安装。
  `0.0.2-beta.3` 及更早版本的应用内自动更新存在缺陷，从那些版本升级请手动下载
  （README「安装」一节有同样说明）。
- **回退**：设置里切回平台默认后端；或重新安装 0.0.2——两种方式都保留配置。
- **设备身份边界（重要）**：SDL3 的设备身份是独立的 `sdl:` 前缀 ID，旧配置到该身份的
  自动迁移**尚未实现**。因此启用 SDL3 后，同一只手柄可能被识别为“新设备”而使用默认
  配置；切回平台默认后端后，原配置仍然完好。这是已知边界，不是配置丢失。

## 已知限制

- SDL3 provider 与探针均未经真机验收；覆盖声明以 SDL 版本和能力记录，不以少数型号
  的成功推导为所有设备已实测。
- 后端切换需要重启（daemon 启动时读取设置），没有运行中热切换。
- Joy-Con 单只与 Pair 是否共享配置的规则未定（S2）。
- 触摸板、体感等扩展输入不在本版范围（S4）；设备未申报或未验证的能力保持禁用。
- “SDL 已声明但物理控件不存在”的显示策略未实现（U2）。
- Windows 的 XInput 无法读取 Guide 键这一旧限制不变；SDL3 下 Guide／Share 的可用性
  取决于设备与 SDL 映射，尚未实测。
