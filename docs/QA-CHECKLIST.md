# DeziroJoy Windows 真机 QA 检查清单

自动化测试覆盖引擎语义、平台映射与 GUI 结构；以下项目必须在 Windows 真机
连接真实手柄后人工验证。建议按顺序执行，每项记录实际结果。

## 1. 启动与连接

- [ ] `dotnet run --project src/DeziroJoy.App` 启动，窗口标题为 "DeziroJoy"（标题栏自定义，深色主题）
- [ ] 插入 Xbox 手柄，左侧"连接"卡片显示设备名（如 `Xbox 兼容手柄 #1`）与 "Xbox 布局"，状态点亮起
- [ ] 右侧手柄可视化器实时反映按键与摇杆位置
- [ ] 拔出手柄，状态点变灰、提示"未检测到手柄"，可视化器显示"未连接"
- [ ] daemon 形态（Windows 提权守护进程）下手柄存在与否以 daemon 快照为准：连接时状态栏
      显示"已连接手柄 · 由常驻守护进程映射"，不会因本地呈现宿主看不到手柄而误报"未检测到手柄"

## 2. 默认映射（Xbox 布局）

启动映射后，逐项验证：

- [ ] 十字键 ↑ ↓ ← → 对应键盘方向键（可在记事本中输入验证）
- [ ] B → Enter
- [ ] A → Esc
- [ ] X → Ctrl+C（先选中一段文本）
- [ ] Y → Ctrl+V
- [ ] 右摇杆满幅推满，鼠标全屏移动；松开摇杆鼠标停止（无漂移）
- [ ] 左摇杆上推 = 页面向↑滚动；下推 = ↓；左右 = 水平滚动（支持水平滚轮的页面/Excel）
- [ ] 摇杆死区生效：轻微触碰不产生输入

## 3. 鼠标速度与精准度（核心差异化）

在"鼠标灵敏度"页：

- [ ] 拖动"最高速度"滑块，实时预览点的移动范围随之变化，与预期方向一致
- [ ] 速度以 px/s 表示；设为同一数值后，更换鼠标 DPI 或显示器，满幅速度表观一致
  （前提：系统指针速度设置保持不变。输出为相对位移，Windows「提高指针精确度」、
  Linux 指针加速度会在其后再次缩放它，因此换系统设置后同值速度会变——这不是缺陷，
  界面文案已说明该边界）
- [ ] 死区滑块：调到 0.4 后，中心 40% 范围内无移动；调回 0.15 恢复灵敏
- [ ] 响应曲线切换：线性 / 精准 / 激进 / 灵敏，预览图形与手感差异明显
- [ ] 平滑时间：0 = 即时跟随（有抖动感）；0.15s = 起步柔、极速仍可达
- [ ] 精准模式：按住左摇杆（L3），右摇杆鼠标速度降至约 35%，松手恢复
- [ ] 垂直反转勾选/取消，摇杆上推的鼠标方向随之反转
- [ ] 慢速微调：轻推摇杆 5%，鼠标以亚像素精度缓慢移动（不卡顿、不丢步）
- [ ] 点击"应用"后设置立即生效，无需重启

## 10. 提权与常驻（UIPI 根因验证）

这是"置顶应用映射失效"的根因项，**必须单独验证**：

- [ ] 以管理员身份运行一个目标程序（如任务管理器、或一个提权的游戏），
      非提权状态下映射对它无效 → 复现原缺陷
- [ ] GUI 通过命名管道启动/连接提权常驻 daemon，映射对同一提权目标生效 → 确认修复
- [ ] 界面显示实际调用 SendInput 的 daemon PID、权限、运行状态与错误，而非 GUI 自身权限
- [ ] `--install-daemon` 注册登录时启动的提权任务，注销重新登录后 daemon 自动运行
- [ ] daemon 运行时 GUI 关闭，映射依然生效（这是 daemon 的意义）
- [ ] `--uninstall-daemon` 移除任务
- [ ] daemon 内存占用远低于 GUI（Linux 实测 49 MB vs 188 MB；Windows 应同量级）

若第 1 项不复现、或第 2 项仍无效，说明根因不是 UIPI，需要重新归因
（见 `docs/ELEVATION-AND-DAEMON.md`；另一种可能是目标程序校验
`RAWINPUTHEADER.hDevice`，那种情况提权无效，需要虚拟 HID 驱动）。

### Linux：同用户常驻与设备访问权（X11/Wayland 均适用）

X11 不是变量：输入走内核级 evdev/uinput，与显示服务器无关。Linux 上不需要提权
（uinput 不受 UIPI 约束，守护进程以当前用户运行），要验证的是**设备访问权**与
**systemd 用户单元**：

- [ ] 手柄已连接且 `ls /dev/input/event*` 能看到节点：GUI「连接」卡片显示设备名，
      daemon 摘要 `devices detected: N`（N>0）
- [ ] 拔掉手柄：GUI 状态区提示检查连接与蓝牙配对（daemon 摘要有对应指引）
- [ ] 用户不在 `input` 组时（`id` 输出无 input）：GUI 状态区与 daemon 摘要都出现
      `sudo usermod -aG input $USER` 指引与 errno，不再静默显示「未检测到手柄」
- [ ] 执行 `sudo usermod -aG input $USER`（或写入
      `/etc/udev/rules.d/99-dezirojoy.rules`：`KERNEL=="event*",GROUP="input",MODE="0660"`
      与 `KERNEL=="uinput",GROUP="input",MODE="0660",OPTIONS+="static_node=uinput"`）后：
      手柄被检测到、映射生效。两种修改都持久（规则落盘、组成员关系落 `/etc/group`），
      差别是生效时机：udev 规则重载后对后续 open 立即生效，组变更要重新登录
      （应用内 opt-in，安装器不注册 udev）
- [ ] 权限区自动显示节点/uinput、udev 规则和 input 组会话状态；具备 pkexec 与 helper 时显示
      「自动修复权限」，否则显示「查看手动修复方法」。没插手柄或无权限缺口时得到"无需修复"，
      不空跑 pkexec；helper 同时 trigger input 与 misc 两个子系统（`/dev/uinput` 属
      misc 子系统），执行后 event* 与 `/dev/uinput` 立即可用，input 组变更仍需重新登录；
      helper 非 0 退出时按钮降级为可照抄的命令，而非宣称已修复
- [ ] `/dev/uinput` 不可写时（`ls -l /dev/uinput` 非当前用户/组）：daemon 摘要的
      `output sink` 一行带出无法打开的原因与修复指引，不再静默降级为空注入；
      注入过程中 `write()` 失败（如虚拟设备被销毁）也不再丢弃返回值——负返回即带 errno
      抛出并指名事件码
- [ ] 设置面板「后台服务」卡片：安装常驻 = 写单元 → `enable` → `start`（无单独
      `daemon-reload`，`enable` 自行 reload），`systemctl --user status
      dezirojoy-daemon.service` 为 active；卡片显示「已安装并正在运行」。启动失败时
      卡片提示查 `journalctl --user -u dezirojoy-daemon` 并可手动重试，不把已成功的启用
      误报成"启用失败」
- [ ] 刷新显示「未启用」时：若原因是 systemd 找不到单元文件（not-found）、单元无
      `[Install]` 段（static）或已被 mask，卡片在启用行旁给出原因与出路，而非一个每次
      刷新原样复现的"未启用"
- [ ] 单元已安装时托盘/渲染进程经 `systemctl --user start` 取 daemon，不另起私有子进程
      （`ps` 里只有一个由单元管理的 `--daemon` 进程，设置卡片的启动/停止作用于它）
- [ ] 单元文件内容：`Restart=on-failure`、`ExecStart` 指向安装的二进制加 `--daemon`、
      `WantedBy=default.target`，且**不**依赖 `graphical-session.target`
      （无图形会话的 SSH/控制台同样要能常驻）
- [ ] 注销重新登录后 daemon 自动运行；`loginctl show-user $USER -p Linger` 为
      `Linger=no` 时退出登录即结束——需 `loginctl enable-linger $USER` 才能跨登录常驻
- [ ] 「登录时自启动」勾选：`~/.config/autostart/DeziroJoy.desktop` 生成，
      `desktop-file-validate ~/.config/autostart/DeziroJoy.desktop` 无错误；
      取消勾选后文件移除
- [ ] 卸载常驻：单元停止、禁用并删除，`systemctl --user status` 显示不存在
- [ ] CLI：`DeziroJoy --install-daemon` / `--uninstall-daemon` / `--install-autostart` /
      `--uninstall-autostart` 在 Linux 全部可用（不再一律 exit 2）
- [ ] daemon 日志：`journalctl --user -u dezirojoy-daemon -f` 能看到启动摘要与设备指引
- [ ] 真机轴校准：满幅推摇杆鼠标达到满速、轻推只到微速；用 `evtest` 选设备后核对申报
      量程（minimum..maximum）与手感一致——量程经 EVIOCGABS 真读，读不到会静默回退默认
      量程（±32767 / 0..255），表现为死区与满幅判定偏差（见权限文档 5.4）
- [ ] X11 静置与持续输入时均无高 CPU 忙轮询：读取线程等待 evdev `poll` 事件；断开/关 daemon 时
      `eventfd` 能唤醒退出；连续鼠标和滚轮输出仍按引擎时钟正常工作
- [ ] X11 手柄连接后连续点击预设切换、Leader 键往返切换：每次按顺序生效，输入线程不卡死，
      不切回旧预设；拔插后仍沿 daemon 持久化的活动槽恢复
- [ ] Wayland 分别验收 GNOME/KDE 等目标桌面：内核输入输出、预设、临时层提示与屏幕键盘可用；
      前台规则在无法读取窗口时保持桌面默认，跟随鼠标回退固定锚点，托盘缺失归因于桌面支持而非误报

## 14. 实体按键直达配置与劫持

这一节的核心：按下实体键就能跳到那个键的配置，且配置期间按键不再被注入。

## 17. 手柄休眠

无线手柄在**无用户输入 15 分钟**后会自动关机。该计时器在手柄固件内，
Windows 没有任何公开 API 可以禁用它或重置它，因此本应用**不提供"保持唤醒"开关**——
做一个实际无效的选项比不提供更糟。

- [ ] 连接手柄后拔掉/休眠，状态栏应显示"手柄已断开连接，可能已进入休眠，
      请按手柄电源键唤醒"，而不是"未检测到手柄，请连接手柄"
- [ ] 若之前从未连接过手柄，状态栏仍显示"未检测到手柄，请连接手柄"
- [ ] daemon 形态下上述两条同样成立：断开文案来自 daemon 快照的存在性翻转，
      未连接文案来自快照从未报告过手柄

已验证无效、故未采用的方案（均有官方文档依据）：

| 方案 | 结论 |
| --- | --- |
| `SetThreadExecutionState` / `PowerCreateRequest` | 文档明确只作用于**系统/显示器**空闲计时器，无一处提及外设，对手柄无效 |
| `XInputSetState(0,0)` 周期性调用 | 民间做法。零值确实会送达设备（`XInputEnable` 文档："even if it is 0"），但是否重置计时器无任何文档依据；PPSSPP、Dolphin、RPCS3、SDL、xenia、x360ce 全部调用 `XInputSetState`，无一实现保活循环 |
| GIP Set Device State = Full power | 微软自家协议规范 MS-GIPUSB 中唯一记录能重置计时器的命令，但**无公开 API 可发送**（微软对开发者的答复："we don't have any public way for an application to send them"） |
| 未公开 IOCTL（`xboxgip.sys` 0x40001C4C） | 需 SYSTEM 权限、仅 USB、完全未公开，不适合普通用户态应用 |

唯一可靠的办法：**用 USB 线连接**。MS-GIPUSB 原文：该计时器
"Not relevant to USB wired-only devices"。

同理，软件也无法唤醒已休眠的手柄——检测到断开时只能提示用户按电源键。

## 18. Alt+Tab 与瞬时掉线（本轮修复）

**症状**：按住映射为 Alt 的手柄键、再点按映射为 Tab 的键，切换器
每次都回到 MRU 第一个窗口，无法连续切换。键盘操作正常；关闭应用窗口
后手柄操作也正常。

**根因**（已定位并修复，提交 225d5e8）：引擎每 tick（2ms）都按
`GetConnected()` 重建运行时表，而 `XInputGetState` 在蓝牙手柄上会瞬时
失败。一次失败就让设备从列表消失 → `Remove()` → `ReleaseAll()` 抬起
正在按住的所有键（包括 Alt）→ 切换器关闭；下一个 tick 设备回来，
引擎重新按下 Alt → 切换器从第 1 位重开。键盘不经过这条链所以正常；
关闭窗口后引擎停止轮询所以也正常。

**修复**：设备必须连续缺席 5 个 tick（2ms 节拍下即 10ms）才真正移除。
UI 的存在性路径（`RefreshPresence` / `SamplePresence`，300ms 节拍）
故意不享受宽限——那里 5 tick 等于 1.5 秒，且引擎停止时没有任何键被按住。

**真机验证步骤**：

1. 将某手柄键映射为 Alt，另一键映射为 Tab
2. 启动映射，按住 Alt，连续点按 Tab 五次
3. 预期：切换器逐窗前进，能到达第 5 个窗口；松手后落在最后选中的窗口
4. 若仍跳回第一个窗口，说明瞬时掉线的频率超出了 10ms 宽限，
   需要提高 `EngineHost.DeviceAbsenceGraceTicks`

**补充观察**：daemon 退出时会打印 `injected: N events · M blocked`
（提交 026c641）。若此处 blocked 非零，说明注入被 UIPI 丢弃，
那是提权问题而非本缺陷。

  已实测确认（蓝牙 Xbox 无线手柄，VID 045E / PID 0B13）：该手柄唯一的
  HID 实例是带 `IG_` 标记的 XInput 虚拟副本，能读到报告描述符但
  `HidD_GetInputReport` 返回 ERROR_INVALID_PARAMETER、`HidD_GetFeature`
  返回 ERROR_INVALID_FUNCTION、阻塞读零报告——即该接口不承载输入，
  额外按键根本不在其中。读取这类按键需要自写过滤驱动（Steam / ReWASD
  的做法），应用层无解
- 当前产品的 Windows XInput 后端仍不可读 Guide：`XINPUT_GAMEPAD.wButtons` 没有 Guide 位
  （真实位定义到 0x0200 后跳到 0x1000，代码中的 `XInputNative.Guide = 0x0400` 是占位常量，
  恒 0），`Windows.Gaming.Input.GamepadButtons` 同样没有 Guide，因此现有通道不报告 Guide——
  可视化器 Guide 元素常灭、映射不被 Guide 触发，均为当前后端的可解释状态。Linux 侧 evdev 经
  `BTN_MODE`(0x13c) 正常映射 Guide，不受影响。Raw Input 不再是唯一可能路线：GameInput v4
  提供系统按钮 reading、后台开关和 XInput 槽位关联，独立探针见
  `tools/GameInputProbe/README.md`。它尚未接入产品，Guide／Share、后台行为和第三方设备覆盖
  仍需逐项真机验收；app-local 运行时的 `EnableBackgroundInput(true)` 按官方文档没有效果。
  GUI 在右侧按键配置区和 Guide 编辑器中继续明确显示当前 XInput 限制
- Windows 在 Xbox Game Bar 缺失或协议处理程序不可用时，连接手柄或按 Guide 可能由系统
  shell 弹出「获取打开此 ms-gamebar 链接的应用」；应用自身不调用该协议，也无法经 XInput
  拦截 Guide。设置页「Windows 手柄兼容性」卡片分两层处置，均只写当前用户、均可逆：
  第一层写入 `HKCU\Software\Microsoft\GameBar\UseNexusForGameBarEnabled=0` 并重新读取核验
  （“允许控制器打开 Game Bar”偏好）；第二层在第一层无效时注册 `ms-gamebar` 协议的
  no-op 处理程序（`HKCU\Software\Classes\ms-gamebar`，命令为 `"DeziroJoy.exe" --noop-gamebar "%1"`），
  由 DeziroJoy 命令行静默吞掉该链接——不启动窗口、不解析 URL、不修改系统录制设置；
  ms-gamebar URI 之外的其他启动方式不主动拦截。
  注册会先记录协议此前的命令（含“此前没有”）。所有权以两件事共同判定：本应用的属主标记
  **且当前命令仍是本应用的 no-op 处理程序**（允许 exe 路径移动的过期自有 handler）。
  「恢复系统默认」在该判定成立时删除本应用的注册并还原记录的命令；**若当前命令已被其他
  程序接管**（第三方改写命令但不知道我们的私有标记），恢复与注册都拒绝执行、原样不动
  （命令、属主标记、备份都不碰），卡片明确报告该状态并建议系统设置或安装/修复 Xbox
  Game Bar——因为只看标记就恢复会删掉对方的处理程序。备份只是**当时当前用户视图
  （HKCU）下的命令影子副本**：它从未记录机器级（HKLM/HKCR 合并视图）或第三方状态，
  恢复不承诺还原它没记录过的东西；若机器级注册存在，移除本应用的按用户覆盖后它自然
  重新生效，这是“移除覆盖”而非“还原副本”。卡片区分“偏好已写入”“已为本用户注册静默
  处理程序”“已被其他程序接管”等状态并显示各自说明；程序移动/更新导致路径过期时会提示
  重新注册。**该注册不保证抑制弹窗**：它只覆盖 `ms-gamebar` 协议本身，部分 Windows 组件
  （实测在部分 Win11 LTSC 上）会以其他上下文触发同一对话框，此时界面与文档的建议是使用
  系统设置（游戏 → Xbox Game Bar）或安装/修复 Xbox Game Bar，而不是依赖本机制。卸载清理：
  `DeziroJoy.exe --uninstall-gamebar-handler`（或卡片内「恢复系统默认」）可随时交还注册；
  Inno 卸载流程还会在删除文件前自动调用同一命令（`[UninstallRun]`，仅当前用户、隐藏运行）。
  **该清理有两个例外**：可执行文件已缺失时条目按 `skipifdoesntexist` 跳过；恢复失败时
  Inno 不因子进程退出码中断卸载——这两种情况下关联可能残留（指向已删 exe 或未被交还），
  需在重新安装后手动运行同一命令清理。上述两层对“设备到达即触发”的路径仍需真机验证
- Linux 上 evdev 走 raw-code 通道，可以识别超出 Xbox 布局的按键；扫描枚举
  `/dev/input` 目录（不再限于 event0..31），无权限/无节点/无手柄三种空结果在 GUI
  状态区与 daemon 摘要中分别给出可操作指引（见第 10 节 Linux 小节）
- 需要 Windows 8+（XInput 1.4）
- Windows 上 SendInput 受 UIPI 约束：非提权进程无法向提权目标注入输入，
  且失败时错误码不指明源于 UIPI。必须提权运行
- Linux 上不需要提权（uinput 内核级接口，不受 UIPI 约束）；常驻通过 systemd
  用户单元实现，退出登录后继续常驻需 `loginctl enable-linger`
- daemon 输出写 stdout：Windows 计划任务运行时需重定向或未来的日志文件；
  Linux systemd 用户单元运行为 `journalctl --user -u dezirojoy-daemon`

      编辑器“捕获键盘”期间按下该组合：在本应用被捕获、原程序不触发
- [ ] 捕获期间按 Esc：取消捕获，按键不泄漏到焦点窗口
- [ ] 捕获武装期间失焦／打开设置／关闭编辑器：捕获立即结束、钩子卸载，键盘恢复
- [ ] UAC 安全桌面与 Ctrl+Alt+Del 不受影响（设计边界）

### 手柄劫持：按键直达映射卡片

- [ ] 开启劫持后按下实体键：直接打开该键的映射配置，其卡片滚动到可见；已有映射开
      既有条目，无映射开新草稿；不保存、不写配置
- [ ] 偏转摇杆：只选中不打开编辑器；摇杆按压（作为按键）直达
- [ ] 关闭劫持：按键立即恢复活动映射行为（注入恢复），武装中的捕获一并结束；
      重启应用后劫持仍为默认关闭（会话级）

### X11 两浮层 EWMH 置顶

- [ ] 按住临时层 Leader：提示浮层显示在目标应用之上；点击穿透保留（不抢焦点、
      不影响目标应用输入）
- [ ] 打开屏幕键盘：同样置顶且不抢焦点；目标应用可继续接收键入
- [ ] 隐藏再显示（或反复触发）：置顶仍然成立
- [ ] 浮层的其他 WM state（如 SKIP_TASKBAR）保留：任务栏不出现浮层条目
- [ ] Wayland 会话：浮层保持原堆叠，无异常、不激活任何窗口

### Game Bar 两层分离与卸载清理

- [ ] 「关闭手柄唤起 Game Bar」：写入并核验当前用户偏好；状态行如实报告
- [ ] 「注册静默处理程序」：注册后 ms-gamebar 链接静默处理，不再弹“选择应用”
- [ ] 「恢复系统默认」：还原注册前命令；此前没有命令则删除键
- [ ] 用其他程序改写 ms-gamebar 命令（模拟接管）：本应用拒绝注册与恢复，不破坏对方
- [ ] 卸载（含静默卸载）：注册被交回或明确失败；失败时设置卡／`--uninstall-gamebar-handler`
      可手动恢复，不留指向已删除 exe 的注册
- [ ] 明确边界：两层均不保证抑制所有弹窗；部分系统组件经其他上下文触发时仍可能
      弹窗，此时用系统设置或安装／修复 Xbox Game Bar
