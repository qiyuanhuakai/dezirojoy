# Windows 后台架构性能基线

> 测量方式：provider 层虚拟手柄 + 真实墙钟循环、引擎、IPC、三进程与 Windows `SendInput`。
> 这不是物理手柄端到端验收，也不证明相对旧版本“手感更稳定”。

## 结论摘要

- 无手柄且 GUI 退出时，daemon 平均 CPU 为 **1.48% 单核**，呈现宿主为 **1.32%**；两者合计工作集平均为 **177.95 MiB**，私有字节平均为 **71.92 MiB**。常驻内存主要在呈现宿主，而不是 daemon。
- 持续鼠标且 GUI 退出时，合计 CPU 为 **5.75% 单核**，合计工作集平均为 **185.50 MiB**；打开 GUI 后分别为 **17.67%** 和 **545.45 MiB**。GUI 打开成本明显，但 GUI 退出后其进程不常驻。
- 代码目标 Tick 间隔为 2 ms，但实测无手柄 Tick p50 为 **15.52 ms**，持续鼠标为 **14.17 ms**，p95 为 **16.00 ms**。因此不能把目标间隔写成实际调度间隔。
- 本矩阵记录 **62081 次成功 SendInput、0 次失败**。持续鼠标场景 Poll→首个 SendInput 返回的 p95 为 **1.63 ms**；该指标不含物理输入送达与目标应用处理时间。
- 120 秒连续鼠标场景中，daemon 工作集从 **58.38→70.62 MiB**，私有字节从 **21.21→31.63 MiB**。这是需要延长观测和定位的增长信号，不能写成“无内存增长”。
- 本报告是当前机器、当前工作区构建的一组可复跑基线，不是跨设备性能承诺。现有数据可以约束后续回归，但不足以宣称已证明“后台轻量”或“手感更稳定”。

## 未覆盖边界

1. 没有物理手柄，因此不测蓝牙／USB／XInput 输入送达、断连重连和休眠恢复。
2. 延迟止于 `SendInput` 返回，不测目标应用接收、处理或画面呈现，不是端到端手感延迟。
3. 不测普通应用与管理员应用的注入差异；daemon 与采集器同为非提权进程。
4. 不做旧版本对照，因此不能证明“更稳定”；120 秒连续运行也不替代长时间挂机与泄漏验收。
5. GUI 开关段使用进程终止，不覆盖用户点击关闭时的优雅清理；多屏、缩放、焦点与浮层位置仍属真机验收。

## P1：Software 渲染 A／B（WSL 内的 Windows 实测）

P1 是渲染模式设置（0.0.5-alpha.4 起设置页「界面渲染（仅 Windows）」）：把 Win32 后端钉为
仅 CPU 软件渲染，另一选项为平台检测（AngleEgl 优先、Software 兜底）。**0.0.5-alpha.5
起的分工**：主 GUI 保留该可选设置（持久化选择 + `DEZIROJOY_RENDER` 环境变量 + `--render`
启动参数，命令行 > 环境变量 > 持久化）；**托盘（常驻呈现宿主）固定 Software**——一个
从不关闭的宿主会为一个图标和两个小浮层让 ANGLE／D3D11 存活整个登录会话；该固定是基线
而非锁定（`DEZIROJOY_RENDER` 仍可覆盖以做诊断对照），持久化选择故意不被托盘读取。
以下为**同机同场景、交替运行**的一次实测（主 GUI），样本量有限，只证明该开关的内存效应
可见，**不证明交互无代价**：

| 渲染模式 | 工作集（MiB） | 私有字节（MiB） | CPU |
| --- | --- | --- | --- |
| 平台检测（默认） | 约 283–289 | 约 185–191 | 与 Software 相比未上升 |
| Software（实验） | 约 163–165 | 约 75–77 | 同上 |

- 口径：WSL 内的 Windows 环境、GUI 进程；启动稳定后采样；与上文虚拟手柄基线
  （无 GUI 的 daemon／呈现宿主口径）**不是同一场景，不可直接比较**。
- **问题现场参考**：当前托盘进程约 **208 MiB 工作集／157 MiB 私有字节**——这是需要
  优化的现场口径，同样不与上表直接比较；它提示呈现宿主仍是常驻内存的主要所在，
  也是 alpha.5 把托盘固定为 Software 的直接理由。
- 未测：动画流畅度、输入到画面延迟、高 DPI／多屏、长时间运行；这些建议在真实
  Windows 机器上复验后再决定主 GUI 是否默认切换。Software 初始化失败时应用启动失败
  （不静默回退），这是该开关的既定设计。

## 内存根因与进程合并边界

- **根因是框架地板，不是应用逻辑**：历史实测（[MEMORY.md](MEMORY.md)，旧架构口径）中
  最小 Avalonia 空窗约 175.8 MB RSS／113.7 MB 私有，DeziroJoy 自身增量约 76.3 MB RSS／
  52.6 MB 私有——即约七成是 Avalonia／Skia／.NET 地板，且地板的大头是 GPU 图形栈
  （Intel Graphics Compiler 81.1 MB、D3D 用户模式驱动与 ANGLE 等）。P1 的 Software
  模式省下的约 120 MiB 工作集正是这块图形栈，不是应用代码。
- **三进程拆分的意义就在于把地板从常驻路径上拿走**：daemon 不加载 UI 栈（常驻但轻），
  GUI 关窗即整体释放，托盘只保留图标与浮层所需的最小栈。按此边界：
  - **daemon 永远不能并入任何 UI 进程**——那等于把 UI 地板变成永久常驻；且 Windows 上
    只有提权进程可向提权目标注入（UIPI），daemon 是注入权威（见
    [ELEVATION-AND-DAEMON.md](ELEVATION-AND-DAEMON.md)）。
  - **托盘不能并入渲染窗口**——托盘不关闭、渲染窗口是可释放的，合并会让 GUI 栈永久常驻。
  - **渲染窗口不能并入托盘**——托盘图标与浮层必须在 GUI 退出后存活，这正是呈现宿主的
    存在理由。
  - 唯一有合并余地的是两个 GUI 侧进程，而它们生命周期相反，结论是保持分离、各自做小
    （托盘固定 Software、GUI 惰性创建／虚拟化／门控）。
- 本文不承诺合并或拆分任一进程；任何此类改动都需按同一方法先取得可复跑的对照数据。
